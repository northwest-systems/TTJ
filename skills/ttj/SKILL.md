# TTJ

適用前に [TTJ Specification v0.1.0](references/specification.md) を読む。規格の正本はこの参照文書とし、以下は運用手順として使う。

## 計画と正式作成

1. 対象リポジトリ、リリース項目、目的、成果物、受け入れ条件と、既存の作業記録を確認する。結果を左右する不足だけを質問する。
2. 独立して進められる作業をTicketに分ける。別Ticketの成果待ちを通常の実行依存にせず、依存する工程は同一TicketのJob列にまとめる。
3. 各Ticketに目的・受け入れ条件と、1件以上の順序付きJobを定義する。Jobごとに目的、作業内容、完了条件、主担当を記録する。正式作成前のDraftでは編集できる。
4. 既存の権限・承認ルールに従い、TicketとJob列を一括で正式作成し、初期状態を `todo` にする。作成後はJob列と定義を固定する。実行担当の引き継ぎは、定義変更と区別して記録する。

記録形式や保存先は利用環境に合わせる。専用ツール、データベース、追加の管理ファイルを一律に導入しない。永続化・競合防止を提供できない環境では、その制約を明示し、完全な準拠実装と称さない。

## 実行と判断

- 開始前に、全先行Jobの完了、Job・Ticket・Taskの開始可能性、主担当、排他的な実行権、前回実行の停止または安全な再試行条件を確認する。同一TicketではJobを並行実行しない。
- 開始記録、必要な親の状態更新、Run・Attemptと実行世代の関連付けを、一貫した更新として確定する。単なる提案や説明で作業開始を捏造しない。
- 状態変更は規格の許可表、ガード、階層規則をすべて照合する。終端状態を再開せず、着手済みの仕事を `todo` に戻さない。
- 計画内のレビュー・入力・CI等の待ちは `waiting` とし、理由・対象・復帰条件を記録する。低優先度や実行枠不足だけで `paused` にしない。
- 明示的な保留は `paused`。新規実行を止め、既存実行に安全な停止を要求し、待機・障害情報を保持する。再開先は現在の条件から判断する。
- 既存計画で続けられない問題は `blocked`。理由・解消条件を記録する。追加作業が必要なら `repairs` Ticketを作り、元Ticket側で解消を再確認する。断念時は承認に従いキャンセルし、必要なら `replaces` Ticketを作る。既存Jobを書き換えない。
- 切断や異常終了だけで `blocked`、`canceled`、`completed` にしない。同じ計画で回復可能なら `doing` を維持する。再開前に古い実行権と実行中プロセスを照合する。
- `activity` は実際の観測から記録する。出力がないことや停止要求の送信を終了確認に代用しない。監視手段がない場合は生存を推測せず、Runがあれば `unknown` とする。

## 引き継ぎと完了

会話やRunの終了をTicketの終了にしない。引き継ぎ時には次を既存の記録先に残す。

- Project・Task・Ticket・現在JobのIDとrevision。
- 固定Job列の参照、現在のstatus、着手履歴、待機・保留・障害と解除条件。
- 成果と検証結果、未達の完了条件、次に許可される操作。
- 対象Run・Attempt・実行権の世代、観測時刻、停止確認または不明点。

再開時は記録と実状態を照合する。履歴や権限を推測で補わない。Jobの完了条件、全JobとTicketの受け入れ条件、Taskの全Ticketの確定と必要範囲の充足を、それぞれ確認してから完了にする。

キャンセル時は未終端の子を同時にキャンセルし、実行権を失効させる。遅延通知は履歴に残せるが、状態を復活させない。

準拠点検には規格第10節の適合条件と確認例を使う。計画の提示、実行済みの操作、観測できた事実、未確認事項を区別して報告する。
